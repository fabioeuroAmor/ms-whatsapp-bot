# WB061 — ACHADO DE CONCORRÊNCIA: lost update na sessão Redis

Número dedicado: `5511900000014`. Sessão preparada com consentimento aceito, histórico vazio, antes do teste.

BODY_B='{"event":"messages.upsert","instance":"sgsm-bot","data":{"key":{"remoteJid":"5511900000014@s.whatsapp.net","fromMe":false,"id":"WB061-B"},"pushName":"QA Conc","message":{"conversation":"pergunta B sobre horario de atendimento"},"messageTimestamp":"1700000123"}}'
( curl -s -o /tmp/respA.txt -w "A status:%{http_code}\n" -X POST http://localhost:8083/webhook/evolution -H "Content-Type: application/json" -d "$BODY_A" & )
( curl -s -o /tmp/respB.txt -w "B status:%{http_code}\n" -X POST http://localhost:8083/webhook/evolution -H "Content-Type: application/json" -d "$BODY_B" & )

## Respostas cruas
```
A status:200
B status:200
```
Ambas as requisições HTTP retornaram 200 normalmente — nenhum erro reportado ao chamador (Evolution API), como esperado (o endpoint sempre responde 200).

**O histórico só contém o par referente à mensagem B ("pergunta B sobre horario de atendimento"). O par da mensagem A ("pergunta A sobre especialidades disponiveis") desapareceu completamente** — nem o `USUARIO` nem o `ASSISTENTE` da mensagem A aparecem em nenhum lugar do histórico final, apesar da requisição A ter retornado 200 e presumivelmente ter sido processada (chamada real ao `sgsm-ia`, log de intent, etc., que não pôde ser inspecionado por falta de acesso ao console — ver WB090).

## Causa raiz confirmada por leitura do código (após observar o efeito ao vivo)

`SessaoService.java` (linhas 33-65):
```java
public SessaoBot obter(String numero) {
    String json = redis.opsForValue().get(SESSAO_PREFIX + numero);
    ... // desserializa e retorna uma cópia em memória
}

public void salvar(SessaoBot sessao) {
    String json = objectMapper.writeValueAsString(sessao);
    redis.opsForValue().set(SESSAO_PREFIX + sessao.getNumero(), json, Duration.ofMinutes(...));
}
```
É um `GET` + `SET` simples, sem `WATCH`/`MULTI` (optimistic locking), sem `Lua script` atômico, sem lock distribuído. Quando duas requisições concorrentes chegam para o mesmo número (cada uma processada em sua própria virtual thread, disparada pelo `WebhookController`), ambas fazem `obter()` a partir do MESMO estado inicial da sessão (histórico vazio), cada uma adiciona seu próprio par USUARIO/ASSISTENTE **à sua cópia em memória**, e cada uma chama `salvar()` — a última chamada a `salvar()` "vence" e sobrescreve inteiramente o que a outra gravou. É um *lost update* clássico (read-modify-write sem isolamento).

## Reprodutibilidade

Testado uma vez de forma clara e isolada (idempotência sequencial em WB060 confirmou que, quando as chamadas NÃO são concorrentes — i.e., uma espera a outra terminar — ambas as mensagens aparecem corretamente no histórico, 2 pares). A diferença de resultado entre WB060 (sequencial, sem perda) e WB061 (paralelo, com perda) isola exatamente o fator concorrência como a causa da perda de dado.

## Resultado — ACHADO DE CONCORRÊNCIA CONFIRMADO (destaque para a entrega)

Duas requisições simultâneas para o mesmo número resultam em perda silenciosa de uma das mensagens do histórico da conversa — sem qualquer erro reportado ao usuário ou à Evolution API (ambas recebem 200). Em um cenário real, isso significa que se um usuário mandar duas mensagens do WhatsApp muito próximas no tempo (comum em conversas reais — "oi" seguido rapidamente por outra mensagem antes da primeira ser processada), uma delas pode simplesmente sumir do contexto da conversa sem nenhum sinal de erro, potencialmente confundindo o RAG em turnos seguintes (contexto incompleto) ou, em cenários mais graves envolvendo `confirmacaoPendente` (ex.: duas mensagens concorrentes, uma criando uma confirmação de AGENDAR e outra tentando confirmá-la), pode causar comportamento inconsistente na máquina de estados da sessão.
