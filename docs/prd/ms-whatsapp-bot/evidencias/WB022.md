# WB022 — pergunta sobre agendar sem estar autenticado

## Requisição (reproduzir)
```bash
curl -s -i -X POST http://localhost:8083/webhook/evolution \
  -H "Content-Type: application/json" \
  -d '{"event":"messages.upsert","instance":"sgsm-bot","data":{"key":{"remoteJid":"5511900000001@s.whatsapp.net","fromMe":false,"id":"TESTID022"},"pushName":"QA Tester","message":{"conversation":"quero marcar uma consulta"},"messageTimestamp":"1700000030"}}'
```
Pré-condição: sessão 5511900000001 com `consentimentoAceito:true`, `accessToken:null`.

## Resposta crua
```
HTTP/1.1 200
X-Content-Type-Options: nosniff
X-XSS-Protection: 0
Cache-Control: no-cache, no-store, max-age=0, must-revalidate
Pragma: no-cache
Expires: 0
X-Frame-Options: DENY
Content-Length: 0
Date: Mon, 24 Aug 2026 22:45:16 GMT
```

## Estado Redis depois (trecho relevante do histórico)
```json
{"papel":"USUARIO","texto":"quero marcar uma consulta"},
{"papel":"ASSISTENTE","texto":"*Claro, João!* Para agendar sua consulta dermatológica, preciso saber a data e horário desejados. Você tem alguma preferência?"}
```
`accessToken` permaneceu `null`. `confirmacaoPendente` permaneceu `null`.

## Resultado observado x esperado

O esperado pelo item era: "resposta pede e-mail cadastrado, `accessToken` continua `null`, **nenhuma** `confirmacaoPendente` é criada".

- `accessToken` continua `null` — OK.
- `confirmacaoPendente` continua `null` — OK.
- **A resposta NÃO pede e-mail.** A resposta do `sgsm-ia` (RAG real, `:8082`) respondeu diretamente pedindo data/horário, como se o agendamento já pudesse prosseguir sem autenticação, e ainda se dirigiu ao usuário como "João" — nome que não corresponde a `pushName` (`"QA Tester"`) nem a nenhum dado da sessão. Isso sugere que o RAG do `sgsm-ia` está retornando uma resposta genérica/de exemplo do corpus de treinamento, sem de fato checar `accessToken` da sessão ou pedir e-mail como o fluxo de negócio esperava.

## Resultado

REPROVADO — comportamento de negócio (pedir e-mail antes de prosseguir com agendamento sem autenticação) não foi observado na resposta real do `sgsm-ia`. Os invariantes de estado (accessToken/confirmacaoPendente permanecerem null) se mantiveram, mas o conteúdo da resposta ao usuário diverge do esperado.

## Causa raiz (lida no código após observar o comportamento ao vivo, para explicar a causa — não para inferir o resultado)

Em `BotOrquestradorService.processar()` (`src/main/java/br/com/sgsm/whatsapp/service/BotOrquestradorService.java`, linhas 125-136), o texto "Para agendar, primeiro preciso confirmar sua identidade..." só é retornado quando `resp.getIntent() == AGENDAR` **e** `sessao.getAccessToken() == null`. A checagem de token existe e é determinística. O que falhou foi a classificação prévia: a resposta real recebida do `sgsm-ia` (`:8082`) para "quero marcar uma consulta" aparentemente não classificou o intent como `AGENDAR` (ou, se classificou, `respostaUsuario` já veio preenchida com um texto que ignora o estado de autenticação — o código não sobrescreve `respostaUsuario` do RAG quando o intent é `CONSULTAR`/`CONVERSAR`, apenas repassa). Como não há acesso ao log em tempo real (ver limitação em WB090), não foi possível confirmar qual intent exato foi retornado nesta chamada — apenas o efeito observável (texto de resposta e estado de sessão).
