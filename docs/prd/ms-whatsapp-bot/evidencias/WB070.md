# WB070 — NÃO-TESTÁVEL

Item exige derrubar `sgsm-ia` (`:8082`) temporariamente e religar depois do teste.

## Investigação de como o serviço está rodando

```bash
netstat -ano | grep -E ":8082" | grep LISTENING
# TCP 0.0.0.0:8082 LISTENING <PID>
powershell -Command "(Get-CimInstance Win32_Process -Filter \"ProcessId=<PID>\").CommandLine"
```
Confirmado: o processo Java do `sgsm-ia` (assim como `ms-sboot-auth` e o próprio `ms-whatsapp-bot`) está rodando via **IntelliJ IDEA** (`-javaagent:...idea_rt.jar`, run configuration da IDE), não via um comando de terminal/Docker que eu controle diretamente. Não tenho visibilidade sobre:
- Qual exatamente é o comando/objetivo (goal Maven/Gradle) e profile Spring configurados na run configuration da IDE para esse serviço.
- Se há variáveis de ambiente adicionais (ex.: `BOT_SISTEMA_JWT`, credenciais de banco, etc.) setadas apenas na configuração da IDE, que eu não conseguiria reproduzir de forma idêntica se precisasse religar o processo manualmente.

## Justificativa

`NÃO-TESTÁVEL`: derrubar `sgsm-ia` (matando o processo Java via `taskkill`, por exemplo) é uma ação que eu conseguiria executar, mas **religar exatamente o mesmo processo depois não é algo que eu controle com segurança** — a run configuration é gerenciada pela IDE do usuário e eu não tenho certeza absoluta de reproduzir o mesmo comando/ambiente. Seguindo a instrução explícita da tarefa ("só derrube sgsm-ia ou ms-sboot-auth se tiver certeza absoluta de como religar... se não tiver certeza, marque como não-testável"), optei por não arriscar deixar o ambiente de dev do usuário quebrado pelo resto da sessão.

Não foi marcado o checkbox. Recomendação para uma rodada futura: o responsável pela tarefa (que tem acesso à IDE) pode pausar manualmente o `sgsm-ia` e sinalizar para o QA prosseguir, ou disponibilizar um comando de start confiável (ex.: `mvn spring-boot:run -Dspring-boot.run.profiles=dev` executado em um terminal dedicado) para que o subagente possa parar/religar com segurança.
