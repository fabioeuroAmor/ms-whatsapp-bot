# WB091 — NÃO-TESTÁVEL (tentativas documentadas)

Item pede para forçar uma exceção não mapeada dentro do fluxo síncrono do controller (antes do `Thread.ofVirtual().start(...)`), de forma que caia no `catch (Exception e)` de `WebhookController.receberEvento()` e ainda assim responda 200, logando "Erro ao processar webhook: ...".

## Leitura do código (para orientar as tentativas, não para inferir o resultado)

`WebhookController.receberEvento()` (linhas 34-74) é bastante defensivo: todo campo potencialmente nulo (`data`, `data.key`, `remoteJid`, `message`, `conversation`/`extendedTextMessage.text`) é checado explicitamente com `if (... == null) return ResponseEntity.ok().build();` antes de qualquer uso. Os DTOs (`EvolutionWebhookPayload.java`) usam apenas `String`/`Boolean` (wrapper, nunca primitivo), então não há risco de `NullPointerException` por auto-unboxing. Não há parsing de número/data na parte síncrona (`messageTimestamp` é `String`, não convertido).

## Tentativas reais executadas

1. **`remoteJid` com número vazio** (`"@s.whatsapp.net"`, sem parte local):
```bash
curl -s -i -X POST http://localhost:8083/webhook/evolution -H "Content-Type: application/json" \
  -d '{"event":"messages.upsert","instance":"sgsm-bot","data":{"key":{"remoteJid":"@s.whatsapp.net","fromMe":false,"id":"WB091-1"},"pushName":"QA","message":{"conversation":"oi"},"messageTimestamp":"1700000150"}}'
```
Resultado: `200`, processado normalmente — sessão `{"numero":"",...}` criada no Redis sem erro algum.

2. **JSON profundamente aninhado** (2000 níveis, ~12KB), tentando estourar limite de profundidade do parser Jackson (potencial `StackOverflowError`/erro não mapeado):
```bash
curl -s -i -X POST http://localhost:8083/webhook/evolution -H "Content-Type: application/json" --data-binary @deepnest.json
```
Resultado: `400 {"detail":"Failed to read request",...}` — o próprio Jackson tem proteção contra profundidade excessiva (`StreamReadConstraints`), rejeitando antes de chegar ao controller. Serviço permaneceu vivo (`ping` de verificação retornou 200 logo depois).

3. Todos os outros edge cases já testados nas seções A, I (WB001-WB009, WB080-WB086) também passaram por essa mesma checagem — nenhum deles produziu comportamento diferente de "200 sem efeito" ou "400/415 do Spring antes de chegar ao controller".

## Conclusão

Não foi possível, com as ferramentas de teste HTTP externo disponíveis (sem modificar código-fonte, o que está fora do escopo deste subagente), encontrar um payload sintaticamente válido (que passe pela desserialização Jackson) capaz de disparar uma exceção não tratada dentro do bloco `try` síncrono de `receberEvento()`. O código está bem protegido contra os edge cases de entrada plausíveis nesse trecho específico.

## Resultado

`NÃO-TESTÁVEL` (não reproduzido apesar de tentativas de boa-fé): não encontrei, dentro do escopo permitido (chamadas HTTP reais, sem alterar código), um caminho realista para forçar esse cenário. Diferente de WB070/WB071 (não-testável por risco ao ambiente), aqui a limitação é a robustez do próprio código — não há um "ponto frágil" identificado nos testes anteriores que sirva de gatilho. Recomendação: se o objetivo é validar especificamente o `catch (Exception e)` do controller, um teste de unidade/mock (fora do escopo deste QA de caixa-preta via `curl`) seria mais apropriado para injetar uma falha sintética nesse trecho.
