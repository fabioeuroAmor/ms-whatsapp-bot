## Passo 5 — "confirmo"
```bash
curl -s -X POST http://localhost:8083/webhook/evolution -H "Content-Type: application/json" \
  -d '{"event":"messages.upsert","instance":"sgsm-bot","data":{"key":{"remoteJid":"5511900000005@s.whatsapp.net","fromMe":false,"id":"WB030-5"},"pushName":"Maria QA","message":{"conversation":"confirmo"},"messageTimestamp":"1700000044"}}'
```
Status: 200.

Redis depois:
```json
{"confirmacaoPendente":null,
"historico":[..., {"papel":"USUARIO","texto":"confirmo"},{"papel":"ASSISTENTE","texto":"*Cadastro concluído!* Seja bem‑vinda, Maria da Silva QA."}],
"dadosCadastro":{"nomeCompleto":"Maria da Silva QA","cpf":"***.***.***-**","dataNascimento":"1990-05-15","email":"qa.wb***.***.***-**00005@teste.com"}}
```

Nota metodológica: o texto de `historico[].ASSISTENTE` é sempre `resp.getRespostaUsuario()` do `sgsm-ia`, gravado ANTES do switch de intents em `processar()` (linhas 108-111 de `BotOrquestradorService.java`) — não é necessariamente o `respostaFinal` de fato enviado ao usuário via `EvolutionApiClient.enviarTexto`. Ou seja, o texto "*Cadastro concluído!*" pode ser apenas a sugestão do RAG, não uma confirmação real de que `executarCadastro()` rodou com sucesso. Por isso a prova real deste item foi buscada nos sistemas dependentes reais (abaixo), não no texto do histórico.

## Verificação real nos sistemas dependentes (prova definitiva)

Paciente NÃO foi criado no `sgsm`:
```bash
curl -s -H "Authorization: Bearer [REDIGIDO]" "http://localhost:8080/v1/api/pacientes" > pacientes.json
grep -o "Maria da Silva QA" pacientes.json   # nenhum resultado
grep -o "qa.wb030[^\"]*" pacientes.json      # nenhum resultado
```
Resultado: 44 pacientes no total no `sgsm`, nenhum correspondente ao nome/e-mail de teste.

Conta NÃO foi criada no `ms-sboot-auth`:
```bash
curl -s -i -X POST http://localhost:8081/v1/api/auth/login -H "Content-Type: application/json" \
  -d '{"email":"qa.wb030.5511900000005@teste.com","senha":"anything"}'
```
Resposta: `401 {"detail":"Credenciais invalidas.",...}` — consistente com "e-mail não cadastrado" (nenhuma conta existe).

## Confirmação direta da causa raiz

Reproduzindo, com `curl` direto contra `http://localhost:8080` (bypassando o bot), exatamente a chamada que `SgsmClient.criarPaciente` faria com os valores mascarados capturados no Redis:
```bash
curl -s -i -X POST http://localhost:8080/v1/api/pacientes -H "Authorization: Bearer " -H "Content-Type: application/json" \
  -d '{"nome":"Maria da Silva QA","cpf":"***.***.***-**","dataNascimento":"1990-05-15","email":"qa.wb***.***.***-**00005@teste.com","telefone":"5511900000005"}'
```
Resposta:
```
HTTP/1.1 400
{"detail":"CPF inválido: ***.***.***-**","instance":"/v1/api/pacientes","status":400,"title":"Requisição inválida","type":"https://sgsm.com.br/erros/argumento-invalido"}
```
Confirma de forma definitiva: o `sgsm` rejeita o CPF mascarado como inválido (formato incorreto). Se `executarCadastro()` de fato rodou, ela teria recebido exatamente este 400 do `sgsm`, caído no `catch (Exception e)` e retornado "Erro ao realizar cadastro..." como `respostaFinal` — mensagem que nunca aparece no `historico` (pois o histórico só grava `resp.getRespostaUsuario()` do RAG, não o `respostaFinal`).

Nota lateral: testado também que `POST /v1/api/pacientes` com `Authorization: Bearer ` (token vazio) retorna `201 Created` normalmente para dados válidos — ou seja, `sistema.jwt` vazio (`BOT_SISTEMA_JWT` não setado no ambiente, valor default `${BOT_SISTEMA_JWT:}`) **não é** o que bloqueia a criação; o bloqueio é exclusivamente o CPF/e-mail mascarados sendo rejeitados pela validação de formato do `sgsm`. (Um efeito colateral desta investigação: alguns pacientes de teste "Teste Auth Empty Bearer..." foram criados no `sgsm` de dev durante a checagem — aceitável em ambiente de dev, registrado aqui para rastreabilidade: `id":"c018522a-794c-4e2b-8dce-41c07d7f6f7f"`, cpf `82523534878`.)

## Resultado

REPROVADO — a sequência de mensagens leva a sessão a um estado aparente de "cadastro concluído" no `historico`, mas **nenhuma chamada real efetiva a `sgsmClient.criarPaciente`/`authClient.registrar` resultou em dado persistido** (nem paciente no `sgsm`, nem conta no `ms-sboot-auth`), e `confirmacaoPendente` não chegou a `tipo:"OTP"` como o item exige — voltou a `null`. Causa raiz confirmada diretamente: os campos `cpf`/`email` chegam mascarados/corrompidos das entidades extraídas pelo `sgsm-ia` (achado independente do `ms-whatsapp-bot` em si, mas que quebra este fluxo ponta a ponta) — o `sgsm` rejeita o CPF mascarado com `400 CPF inválido`, confirmado por chamada direta reproduzindo o payload exato. O erro é engolido silenciosamente porque o texto do histórico é sempre a sugestão do RAG (`resp.getRespostaUsuario()`), nunca o `respostaFinal` real (ver limitação de observabilidade documentada em WB090).
