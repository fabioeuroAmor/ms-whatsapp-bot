# WB023 — pergunta sobre cancelar sem estar autenticado

## Requisição (reproduzir)
```bash
curl -s -i -X POST http://localhost:8083/webhook/evolution \
  -H "Content-Type: application/json" \
  -d '{"event":"messages.upsert","instance":"sgsm-bot","data":{"key":{"remoteJid":"5511900000001@s.whatsapp.net","fromMe":false,"id":"TESTID023"},"pushName":"QA Tester","message":{"conversation":"quero cancelar minha consulta"},"messageTimestamp":"1700000031"}}'
```
Pré-condição: mesma sessão de WB022, `accessToken:null`.

## Resposta crua
```
HTTP/1.1 200
X-Content-Type-Options: nosniff
X-XSS-Protection: 0
Cache-Control: no-cache, no-store, max-age=0, must-revalidate
Pragma: no-cache
Expires: 0
X-Frame-Options: DENY
Content-Length: 0
Date: Mon, 24 Aug 2026 22:45:37 GMT
```

## Estado Redis depois (trecho relevante do histórico)
```json
{"papel":"USUARIO","texto":"quero cancelar minha consulta"},
{"papel":"ASSISTENTE","texto":"*Entendi, vamos cancelar sua consulta.* Por favor, informe a data e horário da consulta ou o número do agendamento."}
```
`accessToken` permaneceu `null`. `confirmacaoPendente` permaneceu `null`.

## Resultado observado x esperado

Esperado: "resposta pede e-mail, sem `confirmacaoPendente`".

- `confirmacaoPendente` continua `null` — OK.
- `accessToken` continua `null` — OK.
- **A resposta NÃO pede e-mail** — pede diretamente data/horário ou número do agendamento, mesmo mode não autenticado. Mesmo padrão observado em WB022: o RAG (`sgsm-ia`) não está checando o estado de autenticação da sessão antes de responder.

## Resultado

REPROVADO — mesma causa raiz de WB022 (ver `evidencias/WB022.md` para a análise de código): a checagem determinística `sessao.getAccessToken() == null` existe em `BotOrquestradorService` para o intent `CANCELAR`, mas só é alcançada se o `sgsm-ia` classificar o texto como `CANCELAR`; o efeito observado sugere que isso não ocorreu (ou que `respostaUsuario` do RAG foi usado diretamente). Estado de sessão (accessToken/confirmacaoPendente) permanece correto.
