# WB042 — CANCELAR apontando para agendamentoId inexistente

Sessão usada: `5511900000007` (autenticada, `perfil:PACIENTE`, mesma de WB041).

## Sequência
```bash
curl -s -X POST http://localhost:8083/webhook/evolution -H "Content-Type: application/json" -d '{"event":"messages.upsert","instance":"sgsm-bot","data":{"key":{"remoteJid":"5511900000007@s.whatsapp.net","fromMe":false,"id":"WB042-1"},"pushName":"QA OTP","message":{"conversation":"Quero cancelar o agendamento de id 00000000-0000-0000-0000-000000000000"},"messageTimestamp":"1700000090"}}'
curl -s -X POST http://localhost:8083/webhook/evolution -H "Content-Type: application/json" -d '{"event":"messages.upsert","instance":"sgsm-bot","data":{"key":{"remoteJid":"5511900000007@s.whatsapp.net","fromMe":false,"id":"WB042-2"},"pushName":"QA OTP","message":{"conversation":"confirmo"},"messageTimestamp":"1700000091"}}'
```
Ambas: `status:200`.

Redis após turno 1 (`confirmacaoPendente` populado):
```json
"confirmacaoPendente":{"tipo":"CANCELAR","payload":{"agendamentoId":"00000000-0000-0000-0000-***.***.***-**0"}}
```
**Achado adicional**: mesmo achado de mascaramento de PII de WB030/WB041 se repete aqui — o RAG mascarou parte do UUID fictício (`00000000-0000-0000-0000-000000000000` virou `...-***.***.***-**0`), tratando um trecho do ID como se fosse CPF. Confirma que o mascaramento é um heurístico genérico de sequência numérica no `sgsm-ia`, não específico de CPF de cadastro.

Redis após turno 2 (confirmação): `confirmacaoPendente` volta a `null`, sem exception não tratada, sem 500 no webhook.

## Verificação real no sgsm — duas reproduções diretas

1. Reproduzindo a chamada exata que `SgsmClient.cancelarAgendamento()` faz (PATCH **sem corpo, sem Content-Type** — conforme código-fonte lido após o teste, para explicar o resultado):
```bash
curl -s -i -X PATCH "http://localhost:8080/v1/api/agendamentos/00000000-0000-0000-0000-000000000000/cancelar" -H "Authorization: Bearer [REDIGIDO]"
```
Resposta: `400 {"detail":"Failed to read request",...}`.

2. Mesma chamada, com corpo JSON vazio (`{}`) apenas para confirmar que o endpoint sabe diferenciar "não encontrado" quando a requisição é bem formada:
```bash
curl -s -i -X PATCH "http://localhost:8080/v1/api/agendamentos/00000000-0000-0000-0000-000000000000/cancelar" -H "Authorization: Bearer [REDIGIDO]" -H "Content-Type: application/json" -d '{}'
```
Resposta: `404 {"detail":"Agendamento não encontrado: 00000000-0000-0000-0000-000000000000",...}`.

**ACHADO 3 (mais amplo que este item)**: como `SgsmClient.cancelarAgendamento()` não envia `Content-Type`/corpo, o `sgsm` responde `400 Failed to read request` para **qualquer** tentativa de cancelamento — inclusive com um `agendamentoId` real e existente — antes mesmo de chegar à lógica de "agendamento não encontrado". Ou seja, o fluxo CANCELAR está quebrado de forma mais ampla que só o caso de ID inexistente coberto por este item.

## Resultado

APROVADO (para o critério específico do item) — não houve 500 não tratado; o erro (400 do `sgsm`, por requisição malformada) foi capturado pelo `catch (Exception e)` de `executarCancelamento()` e a sessão retornou a um estado consistente (`confirmacaoPendente:null`, sem travar). O texto exato de erro mostrado ao usuário não pôde ser confirmado (limitação de observabilidade, ver WB090), mas o comportamento de resiliência (sem crash, sessão não corrompida) está confirmado.

Achado registrado para a Fase 5: o cancelamento real (`PATCH /v1/api/agendamentos/{id}/cancelar` sem corpo) falha com `400` mesmo para IDs válidos, por ausência de `Content-Type`/corpo na chamada feita por `SgsmClient.cancelarAgendamento()` — isso é mais amplo que o escopo original deste item (que testava apenas "ID inexistente"), mas foi descoberto ao reproduzir a chamada real para confirmar o resultado.
