**ACHADO 1**: `pacienteId` está `null` no payload — mesmo com a sessão autenticada (`accessToken` válido, `perfil:PACIENTE`). Confirma, ao vivo, o que a leitura do código já sugeria: `SessaoBot.usuarioId` nunca é atribuído em nenhum ponto do código (`processarOtp()` só seta `accessToken`/`refreshToken`/`perfil`), então `montarPayloadAgendamento()` (`BotOrquestradorService.java` linha ~258, `payload.put("pacienteId", sessao.getUsuarioId())`) sempre envia `null`.

**ACHADO 2**: `data` está no formato `"30/08/2026"` (DD/MM/AAAA, como o usuário digitou) em vez de `"2026-08-30"` (ISO, exigido por `combinarDataHora()` em `ExecutorAcaoService.java`, que apenas concatena `data + "T" + hora`).

Nenhum agendamento para 30/08/2026 apareceu em `GET /v1/api/agendamentos`:

Reprodução direta do payload exato que `ExecutorAcaoService.executarAgendamento()` enviaria (`pacienteId:null`, data concatenada sem conversão de formato):

```bash
  -d '{"pacienteId":null,"servicoMedicoId":"241760a1-efdc-44c6-b3c2-1f3a64013fe4","dataHoraInicio":"30/08/2026T10:00:00"}'
```

Confirma que o `sgsm` rejeita a requisição (falha de parse do formato de data — `LocalDateTime`/`Instant` do Spring não aceita `"30/08/2026T10:00:00"`).

## Resultado

REPROVADO — nenhum agendamento real foi criado no `sgsm`. Duas causas raízes identificadas e confirmadas por chamada direta reproduzindo o payload exato:
1. `SessaoBot.usuarioId` nunca é atribuído após autenticação via OTP — `pacienteId` sempre `null` em qualquer agendamento tentado por este fluxo.
2. `ExecutorAcaoService.combinarDataHora()` não normaliza o formato de data recebido do RAG (aceita `DD/MM/AAAA` do usuário sem converter para ISO `AAAA-MM-DD`), gerando uma string de data-hora inválida para o `sgsm`.

Qualquer uma das duas causas isoladamente já impediria o agendamento; juntas, tornam o fluxo AGENDAR (autenticado, dados completos) inoperante neste ambiente, mesmo quando o usuário fornece IDs de médico/serviço reais e válidos.
